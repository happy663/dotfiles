# インラインレビュー拾い上げスキル

コード・Markdownファイル内に書かれた `review-comment:` マーカーを抽出し、各指摘の意図を整理して議論する。必要な場合だけコードを修正し、対応したマーカーを自動で削除する。GitHub PR の inline review コメントに相当するワークフローをローカルで完結させる。

## マーカー記法

### 形式1: コード内コメント

`review-comment: <本文>`

* 言語のコメント記号 (`//`, `#`, `--`, `<!--`, `;` 等) は問わない。`review-comment:` を含む行を全て対象にする
* マーカーは単一行を基本とする
* 番号なしの連続する `review-comment:` 行は1つのコメントとして結合する

例:

```ts
function calculate(x) {
  // review-comment: edge caseでマイナス値を考慮して
  return x * 2;
}
```

### 形式2: Markdown blockquote

`> 📝 review-comment: <本文>`

* Markdown ドキュメント用の記法
* コード内コメントと同様に検出・削除対象とする
* blockquote 行は「専用コメント行」として行ごと削除する

例:

```markdown
これはテスト用のドキュメントです。
> 📝 review-comment: 具体的な例に差し替えて
```

### 番号マーカー方式（語句単位レビュー用）

コメントに番号 `[N]` を付け、本文中の対象語句の直後にも同じ `[N]` を置くことで、行ではなく語句単位のレビューを表現する。

* コメント: `> 📝 review-comment: [1] <本文>`
* 対象位置: 本文中、対象語句の直後に `[1]` を付与（例: `テスト用[1]のドキュメント`）
* コメントの `[N]` と本文側の `[N]` が対応する
* 番号はドキュメント内の既存番号の最大値+1（連番）で採番する

例:

```markdown
これはテスト用[1]のドキュメントです。
> 📝 review-comment: [1] 具体的な例に差し替えて
```

## 手順

### 1. 検索範囲の決定

* 引数あり → 指定パス（ファイル or ディレクトリ）に限定。複数パス可
* 引数なし + git管理下 → `main` との差分ファイルを優先する
    * `git diff --name-only main...HEAD`
    * `git diff --name-only`
    * `git diff --cached --name-only`
    * 必要に応じて `git ls-files --others --exclude-standard`
* `main` が存在しない場合は `origin/main`、`master`、`origin/master` の順で利用可能なベースを探す
* `--all` 指定時のみ → `git ls-files` の出力（git追跡ファイル全体）
* git管理外のディレクトリで引数なし起動 → ユーザーに対象パスの指定を求める

### 2. マーカー抽出

git管理下の追跡ファイルは `git grep` を優先で使用する。

```bash
git grep -n 'review-comment:' -- <scope>
```

指定パス、未追跡ファイル、または `git grep` で扱いにくい対象は `rg --hidden` を使用する。

```bash
rg --hidden -n --no-heading 'review-comment:' <scope>
```

* `rg` が利用不能な場合は Grep ツールへフォールバック
* 文字列リテラルやスキル仕様本文など、レビューコメントではない可能性が高い検出結果は「候補外」として分類し、実レビュー件数に含めない
* 結果を以下の構造にまとめる
    * path: 絶対パス
    * line: 1始まり行番号
    * comment: マーカー以降の本文（前後空白trim）
    * context: 前後5行（行番号付き）

抽出後の整理:

* コメントの番号（`[N]`）を抽出する
* 番号付きコメントは、同一ファイル内の本文側 `[N]` マーカーと対応付ける
* 番号が異なる連続するコメント（`[1]` と `[2]` など）は**別コメントとして扱う**（結合しない）。番号なしの連続行のみ1つのコメントに結合する
* 対応する本文側 `[N]` が見つからないコメント、および本文側にあってコメントがない `[N]` は「整合性チェック」（手順4.5）に回す

### 3. 結果の提示

* マーカー0件 → 「`review-comment:` マーカーが見つかりませんでした（検索対象: ○件）」と明示してskill終了
* 1件以上 → ファイル単位でグルーピング、各マーカーに通し番号 (#1, #2, ...) を付与し、周辺コードと共に一覧表示
* 番号付きコメントは周辺コードではなく、**対象語句（`[N]` が付いた箇所）** を中心に表示する

出力イメージ（コード内コメント）:

```
src/foo.ts
  #1  L42  edge caseでマイナス値を考慮して
      40 | function calculate(x) {
      41 |   // review-comment: edge caseでマイナス値を考慮して
      42 |   return x * 2;
      ...
```

出力イメージ（blockquote・番号マーカー方式）:

```
docs/guide.md
  #1  [1] テスト用 → 具体的な例に差し替えて
      L3 | これはテスト用[1]のドキュメントです。
      L4 | > 📝 review-comment: [1] 具体的な例に差し替えて
```

* 対象語句の行が長い場合は `[N]` を含む行を省略せずに表示し、どこの語句に付いたかを明確にする

### 4. 指摘の分類と見解提示

* 各マーカーを最初に分類する
    * `要修正`: 指摘が妥当で、コード変更が必要
    * `要議論`: 指摘は妥当そうだが、設計判断・トレードオフ・仕様確認が必要
    * `説明のみ`: 「なぜそうしたのか」を知りたい質問で、すぐに修正すべきではない
    * `対応不要`: 指摘が誤解、既存制約と矛盾、または変更しない方がよい
* 分類ごとに、判断理由を具体的に書く
* `説明のみ` はコード変更案ではなく、該当実装の意図・背景・代替案との比較を説明する
* `対応不要` は単に拒否せず、なぜ変更しない判断が妥当か、必要なら代替コメント案を出す
* `要議論` は確認したい論点を明示し、すぐに編集しない
* `要修正` のみ、具体的な対応案をチャットに出力する
* 文字列リテラル内に `review-comment:` が含まれている疑いがあれば「これは文字列内の可能性があります、対応対象から外しますか？」と注記する
* 対応案は変更内容と理由を明示する（CLAUDE.md「Pre-Edit Explanation Requirement」遵守）

### 4.5 整合性チェック（番号マーカー方式のみ）

番号マーカー方式のコメントが存在する場合、以下を確認して警告する:

* コメントに `[N]` があるのに、本文側に対応する `[N]` がない → 「対象マーカーが見つかりません」と警告し、コメントの対応先をユーザーに確認する
* 本文側に `[N]` があるのに、対応するコメントがない → 孤立マーカーとして警告し、対処方針（削除するか残すか）をユーザーに確認する
* 同じ番号のコメントが複数ある → 重複番号として警告する（採番ミスの可能性）

### 5. 議論と方針決定

* ユーザーに「どの分類・方針で進めるか」を確認する
* ユーザーが質問しているだけの場合は、回答して skill を終了してよい
* ユーザーが説明に納得し、修正不要と判断したマーカーはコードを変えない
* 修正するマーカーがある場合だけ「この内容で適用してよいか」を確認する
* 承認後、Edit ツールで対象マーカーへの対応をまとめて適用する
* `要議論`、`説明のみ`、`対応不要`、ユーザーがスキップ判断したマーカーは修正しない

### 6. マーカー削除（自動）

コード修正したマーカー、またはユーザーが「説明で解決」「対応不要で解決」と明示したマーカーは自動で削除する。未解決・要議論・スキップ判断したマーカーは残す。

削除方法は行の構造で分岐する:

* 専用コメント行（行頭からコメント記号と空白、その後 `review-comment:` のみ、および Markdown blockquote の `> 📝 review-comment: ...` 行）→ 行ごと削除
* 行末マーカー（コードの末尾にコメントとして付与されている）→ マーカー部分のみ削除しコードを残す
* 番号マーカー方式のコメントを削除する場合は、**本文側の対応する `[N]` マーカーも同時に削除する**

判定例（コード内コメント）:

```ts
// 行ごと削除されるパターン
  // review-comment: マイナス値を考慮して

// マーカー部分のみ削除されるパターン
  return x * 2;  // review-comment: 戻り値の型を見直して
  // ↓
  return x * 2;
```

判定例（blockquote・番号マーカー方式）:

```markdown
<!-- 行ごと削除されるパターン（コメント行 + 本文側 [N]） -->
これはテスト用[1]のドキュメントです。
> 📝 review-comment: [1] 具体的な例に差し替えて
<!-- ↓ 解決後 -->
これはテスト用のドキュメントです。
```

本文側 `[N]` の削除手順:

* 削除対象のコメント番号に対応する `[N]` を、同一ファイル内の本文から `\[N\]` で検索して削除する
* 同じ `[N]` が複数箇所にある場合は、全て削除する（またはユーザーに確認する）
* `[N]` 削除後に前後に不要な空白が残る場合は整形する（例: `テスト用[1]の` → `テスト用の`）

### 7. サマリ出力

最後に以下を出力する:

* 対応済み件数
* 説明で解決した件数
* 対応不要として解決した件数
* スキップ件数
* 残ったコメントマーカー一覧（path:line と本文）
* 残った本文側マーカー `[N]` 一覧（path:line と対象語句）

## 注意事項

* 文体は常体（だ・である調）で統一する
* 文字列リテラル内のマーカー誤検出は ripgrep の段階で区別不能。AI が判断し疑いがあればユーザーに確認する
* レビューコメントは命令ではなく、議論の入口として扱う。言われた内容を無条件に実装しない
* 編集は必ず承認後に実行する。事前確認なしの自動編集は行わない
* 削除はマーカー単位で行う。ファイル全体を上書きするような操作は避ける
* 番号付きコメント（`[N]`）を解決する場合は、コメント行と本文側マーカーの両方を削除する。片方だけ残すと孤立マーカーになる
* blockquote 形式（`> 📝 review-comment:`）は Markdown ドキュメント内で使う。コードファイルでは従来のコメント記号を使う
